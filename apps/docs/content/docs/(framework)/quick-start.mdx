The repository contains a complete working setup: an example Next.js host, an example theme and a
mock external API. It is the fastest way to see puck-remote running, and the way to use it until
the packages are published.

## Requirements

- **Node 26**: native arm64 on Apple Silicon (`node -p process.arch` → `arm64`), x64 or arm64 on
  Linux. `.nvmrc` says `26`.
- **pnpm 12**: `npm i -g pnpm` (Node 26 no longer bundles corepack).

<Steps>
<Step>

### Install and build the packages

```bash
pnpm install
```

```bash
pnpm build
```

Packages ship compiled ESM; `pnpm dev` keeps them rebuilding in watch mode.

</Step>
<Step>

### Start the mock API

```bash
pnpm --filter mock-api start
```

It listens on `http://localhost:4010` and backs the theme's `events` adapter.

</Step>
<Step>

### Start the host

```bash
pnpm --filter host dev
```

| What | URL |
|---|---|
| Public site | `http://localhost:3100/` (or `http://site.localhost:3100/`) |
| Search page (uncacheable) | `http://localhost:3100/search?q=nonce` |
| Admin login (demo: `admin` / `admin`) | `http://admin.localhost:3100/login` |
| Admin dashboard (theme library: Customize, Preview, Publish, Delete) | `http://admin.localhost:3100/` |
| Admin page (editor frame + Publish) | `http://admin.localhost:3100/editor` (served by `/admin/editor`, requires the login); `?previewPath=/search` opens the template of that page, `&theme=<id>` another theme |
| Editor (embedded only, served by the same app) | `http://127.0.0.1:3100/` |

One app answers all three origins: `*.localhost` resolves to loopback, so the site and the admin
pages are two origins, and `127.0.0.1` is another site for the editor. On the editor origin only
the editor page is reachable, at `/`, and every other path is 404. On the admin hostname, every
path is served from the app's `/admin` pages (`/editor` → `/admin/editor`). `/admin` and the editor page
(`/theme/editor`) answer 404 on the public site.

</Step>
<Step>

### Publish the example theme

With the host running, publish through its artifacts API. `examples/theme/puck-remote.cli.ts`
gives the CLI the API's URL and the token the example app accepts (`dev-token` in development):

```bash
pnpm --filter theme release
```

This runs `puck-remote push --live`: it builds the theme, uploads it to
`http://admin.localhost:3100/api/themes` and points the main theme at it (created on the first
push): `examples/app/data/artifacts/themes.json` and the theme's files in
`examples/app/data/artifacts/themes/<id>/`. Running it again sends only what changed. Reload the site.

</Step>
<Step>

### Change the theme

Templates edited in the admin page live in the theme's files on the host. Bring them into the theme repo first:

```bash
pnpm --filter theme pull
```

Then work on your device's development theme, without touching the live site (the example enables
[several themes](/docs/concepts/themes)):

```bash
pnpm --filter theme dev
```

It creates `Development (<hash>-<your device>)` on the first run, pushes only the changed files to it
after every change in `examples/theme` and prints a preview link for `http://localhost:3100`: open it, and the page reloads
by itself after each push (live reload). The dashboard lists the
themes, with Customize, Preview, Publish and Delete. When you are done, run `release` again: the
host switches the main theme at once, with no restart. Themes keep only their current files: to
roll back, check out an older version of `examples/theme` and run `release` again.

</Step>
</Steps>

## What's in the repository

```files
puck-repository-poc
├── packages
│   ├── sdk
│   ├── cli
│   ├── core
│   ├── next
│   ├── editor
│   ├── artifacts-fs
│   └── source-mock
├── apps
│   ├── host
│   └── docs
├── examples
│   └── theme
├── mock
│   └── api-server
├── artifacts
└── data
```

| Path | Content |
|---|---|
| `packages/sdk` | `@puck-remote/sdk`: theme API and host contracts |
| `packages/cli` | `@puck-remote/cli`: build, publish, pull, activate |
| `packages/core` | `@puck-remote/core`: the engine |
| `packages/next` | `@puck-remote/next`: Next.js bindings |
| `packages/editor` | `@puck-remote/editor`: `<PuckRemoteEditor>` (editor page), `<PuckEditorFrame>` (admin page), protocol |
| `packages/artifacts-fs`, `source-mock` | File-based and example adapters |
| `examples/app` | Example Next.js app (public site, admin page, editor), with its data |
| `apps/docs` | This documentation |
| `examples/theme` | Example theme (the "developer repo"), with its pages |
| `examples/app/mock/api-server` | External API stand-in |
| `examples/app/data` | The site's themes and their files (`artifacts/`, git-ignored) and CMS seed data (`cms.json`) |

## Useful commands

| Task | Command |
|---|---|
| Tests | `pnpm test` |
| Typecheck | `pnpm typecheck` |
| Package lint | `pnpm lint:pkg` |
| Benchmarks | `pnpm --filter @puck-remote/core bench` |
| Docs | `pnpm docs:dev` (port 3200) |

Auth belongs to the app. In development the example's admin page and RPC route are open; in
production they require `PUCK_REMOTE_ADMIN_TOKEN` (see [Environment](/docs/environment)).

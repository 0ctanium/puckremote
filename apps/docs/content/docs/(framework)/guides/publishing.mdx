---
title: Templates and publishing
description: Templates live in the theme, like Shopify templates; your app picks which one a route renders; saving a template creates an artifact; publishing workflows are plugins.
---

Templates are part of the theme ([D-0188](/docs/internal/decisions#D-0188),
[D-0386](/docs/internal/decisions#D-0386)). A theme repo has a `templates/` folder next to its
blocks, and every artifact carries the templates it was published with:

```files
my-theme
├── blocks
│   └── hero.tsx
├── root.tsx
└── templates
    ├── home.json
    ├── product.json
    └── blog
        └── post.json
```

`templates/<name>.json` is Puck data with any root props. The build checks that every item uses a
block of the theme and fails otherwise, so a template never ships with code it doesn't fit.

## Routes pick templates

The core never maps URLs to templates ([D-0371](/docs/internal/decisions#D-0371)). Each route of
your app chooses a template and passes the **params** its blocks need
([D-0374](/docs/internal/decisions#D-0374)):

```ts
// /products/[handle] → one template for every product
await remote.loadTemplate('product', { params: { handle } })
// a catch-all → the template named like the path (the example app)
await remote.loadTemplate(name, { params: { slug: name } })
```

Blocks read params with `{ $params: 'handle' }` in their data specs and `ctx.params` in render.
Your route also builds the page metadata from the template's root props (for example the
`title` and `description` [root fields](/docs/configuration#root-fields) your app declares).

## The two primitives

The core only reads and writes templates ([D-0190](/docs/internal/decisions#D-0190),
[D-0387](/docs/internal/decisions#D-0387)):

```ts
const template = await core.readTemplate('home') // current artifact, or { artifact: id }
const { id } = await core.writeTemplate('home', data, { base: template.artifact })
```

`writeTemplate` validates and cleans the data (resolved editor data is removed), writes it into a
**copy** of `base` (same code, same other templates) and returns the new artifact's id. It never
changes what the site serves. Making it live is a separate step:

```ts
await core.config.artifacts.writePointer(id)
```

## Publishing workflows are plugins

Everything else is your app's choice, built on these primitives:

- **Save = publish** (the example app): write the template, move the pointer. It refuses when the
  pointer moved since the editor opened, so an older base never undoes newer changes.
- **Drafts**: write templates to artifacts without moving the pointer; keep the draft artifact id
  in your database; publish = move the pointer.
- **History and rollback**: artifacts are immutable, so keeping their ids is the history;
  rollback = move the pointer back.

Who may do what is checked by your app with its own session, never by the editor.

## Developers and editors working together

Like Shopify, the content edited in the editor lives in the theme's artifacts. Before publishing
new code, bring those changes into the theme repo:

```bash
puck-remote pull --artifacts <store>
```

`pull` writes the current artifact's templates into `templates/`. Change blocks and the templates
that use them together, build, and publish. Publishing uploads code **and** templates as they are
in the repo, so templates edited since your last pull are replaced.

Artifacts built before templates (with a `pages/` folder) are refused: rebuild and republish the
theme ([D-0377](/docs/internal/decisions#D-0377)).

---
title: Templates and publishing
description: Templates live in the theme, like Shopify templates; your app picks which one a route renders; saving a template writes it into the theme; publishing workflows are plugins.
---

Templates are part of the theme ([D-0188](/docs/internal/decisions#D-0188),
[D-0386](/docs/internal/decisions#D-0386)). A theme repo has a `templates/` folder next to its
blocks, and every theme carries the templates it was pushed with:

```files
my-theme
├── blocks
│   └── hero.tsx
├── root.tsx
└── templates
    ├── home.json
    ├── product.json
    └── blog
        └── post.json
```

`templates/<name>.json` is Puck data with any root props. The build checks that every item uses a
block of the theme and fails otherwise, so a template never ships with code it doesn't fit.

## Routes pick templates

The core never maps URLs to templates ([D-0371](/docs/internal/decisions#D-0371)). Each route of
your app chooses a template and passes the **params** its blocks need
([D-0374](/docs/internal/decisions#D-0374)):

```ts
// /products/[handle] → one template for every product
await remote.loadTemplate('product', { params: { handle } })
// a catch-all → the template named like the path (the example app)
await remote.loadTemplate(name, { params: { slug: name } })
```

Blocks read params with `{ $params: 'handle' }` in their data specs and `ctx.params` in render.
Your route also builds the page metadata from the template's root props (for example the
`title` and `description` [root fields](/docs/configuration#root-fields) your app declares).

## The two primitives

The core only reads and writes templates ([D-0190](/docs/internal/decisions#D-0190),
[D-0387](/docs/internal/decisions#D-0387)):

```ts
const template = await core.readTemplate('home') // main theme, or { theme }
const { hash } = await core.writeTemplate('home', data, { theme: template.theme, expect: template.hash })
```

`writeTemplate` validates and cleans the data (resolved editor data is removed) and writes it into
the [theme](/docs/concepts/themes): `templates/home.json` and the updated manifest, nothing else
([D-0517](/docs/internal/decisions#D-0517)). `expect` refuses the save (`ThemeError`, 409) when the
theme changed since that hash, so an older version never undoes newer changes. Saving into the main
theme changes the live site; to prepare changes first, save into another theme and publish it.

## Publishing workflows are plugins

Everything else is your app's choice, built on these primitives:

- **Save = publish** (the example app): write the template into the theme the editor was opened on
  (the main theme, or another one with `?theme=<id>`), with `expect` = the hash the editor started
  from, so a `puck-remote dev` push in between is never undone.
- **Drafts**: with [several themes](/docs/concepts/themes), edit an unpublished theme (`duplicate`
  the main one) and publish it (`core.themes.publish`).
- **History and rollback**: themes keep only their current files. Keep history in git (the theme
  repo, after `pull`) or in your own storage; rollback = push an older checkout.

Who may do what is checked by your app with its own session, never by the editor.

## Developers and editors working together

Like Shopify, the content edited in the editor lives in the theme's files. Before pushing
new code, bring those changes into the theme repo:

```bash
puck-remote pull
```

`pull` writes the main theme's templates into `templates/` (`-t` for another theme). Change blocks and the templates
that use them together, build, and publish. Publishing uploads code **and** templates as they are
in the repo, so templates edited since your last pull are replaced. To work on code without touching
the site, use your development theme: see [Local theme development](/docs/guides/theme-dev).

Artifacts built before templates (with a `pages/` folder) are refused: rebuild and republish the
theme ([D-0377](/docs/internal/decisions#D-0377)).

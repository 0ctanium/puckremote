title: Adapters
description: Everything backend-specific is a pluggable contract; the core stays agnostic.

The core depends only on contracts from `@puck-remote/sdk/host`. The app picks implementations in
one file, `puck-remote.config.ts` ([D-0035](/docs/internal/decisions#D-0035)).

| Contract | Purpose | Default / example |
|---|---|---|
| `DataSource` | Answers `find`/`findByID`/`global` | `@puck-remote/source-mock` (example) |
| `ArtifactStore` | Theme artifacts (code and pages) + current pointer | `@puck-remote/artifacts-fs` |
| `RendererFactory` | Where theme code runs | `workerPoolRenderer()`; `inProcessRenderer()` |

Pages are part of the artifact ([D-0188](/docs/internal/decisions#D-0188)), so there is no separate page
store. Authentication, caching, drafts, review and history are not core concerns
([D-0187](/docs/internal/decisions#D-0187), [D-0190](/docs/internal/decisions#D-0190)): your app owns its sessions,
and publishing workflows are plugins built on `readTemplate`, `writeTemplate` and the artifact pointer
(see [Templates and publishing](/docs/guides/publishing)).

## Two very different kinds of "adapter"

- **Host plugins** (the table above) are **trusted** Node code chosen by the operator.
- **Theme adapters** (`defineAdapter` in `adapters/*.ts`) are **untrusted**, shipped by the theme,
  **sans-IO**: two synchronous functions (`toRequest`, `fromResponse`) that run in the isolate and
  translate between a query and an HTTP request/response the host performs.

## Enforcement stays in the core

Plugins only implement storage semantics. The core does policy (allowed fields, operators,
limits, projection), hashing and validation of artifacts and pages, and the draft/public mode
split. That way a buggy plugin cannot widen what a theme can reach.

A contract test suite in `@puck-remote/core/testing` lets store authors check their
implementation ([D-0067](/docs/internal/decisions#D-0067)). See [Core › Adapters](/docs/core/adapters).

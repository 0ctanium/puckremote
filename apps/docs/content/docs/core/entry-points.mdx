title: Entry points
description: What each import path of @puck-remote/core provides, and where it is safe to use.
---

| Import | Content | Loads the sandbox? |
|---|---|---|
| `@puck-remote/core` | `createCore`, renderers, auth helpers, errors, types | yes (lazily) |
| `@puck-remote/core/config` | `defineConfig`, `devAllowAll`, `sharedSecretAuth`, `memoryCache` | no |
| `@puck-remote/core/edge` | Request classification, security headers, page cacheability | no |
| `@puck-remote/core/react` | `PuckRemotePage`, `pageMetadata` (server components) | no |
| `@puck-remote/core/editor` | `EditorClient` (client component) | no |
| `@puck-remote/core/testing` | Adapter contract test suites (vitest) | no |

Use `/config` in your config file and `/edge` in middleware or proxies: they never import
isolated-vm.

## `@puck-remote/core`

`createCore`, `defineConfig`, `resolveConfig`, `DEFAULT_ROUTES`, `normalizeSlug`,
`AccessDeniedError`, `CSRF_HEADER`, `devAllowAll`, `sharedSecretAuth`, `classifyRequest`,
`surfaceOf`, `WrongSurfaceError`, `memoryCache`, `inProcessRenderer`, `workerPoolRenderer`,
`bubblewrap`, `workerLaunchOptions`, and the types.

## `@puck-remote/core/react`

- `<PuckRemotePage page={page} />`: renders a `PreparedPage` (server component).
- `pageMetadata(page)`: `{ title, description, other }`, compatible with Next's `Metadata`.

## `@puck-remote/core/editor`

- `<EditorClient {...editorProps} />`: the Puck editor (client component). Blocks are rendered
  on the server through the API; no theme JavaScript runs in the browser.

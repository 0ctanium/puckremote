title: Entry points
description: What each import path of @puck-remote/core provides, and where it is safe to use.
---

| Import | Content | Loads the sandbox? |
|---|---|---|
| `@puck-remote/core` | `createCore`, renderers, errors, types | yes (lazily) |
| `@puck-remote/core/config` | `defineConfig`, `resolveOrigins` | no |
| `@puck-remote/core/edge` | Security headers, request origin, page cacheability | no |
| `@puck-remote/core/react` | `PuckRemotePage`, `pageMetadata` (server components) | no |
| `@puck-remote/core/testing` | The artifact store contract test suite (vitest) | no |

Use `/config` in your config file and `/edge` in middleware or proxies: they never import
isolated-vm. The editor lives in its own package, `@puck-remote/editor`
(`/protocol`, `/frame`, `/bridge`; see [The editor](/docs/concepts/editor)).

## `@puck-remote/core`

`createCore`, `defineConfig`, `resolveConfig`, `DEFAULT_ROUTES`, `normalizeSlug`, `ConfigError`,
`PageError`, `MAX_PAGE_BYTES`, `UnknownBlockError`, `inProcessRenderer`, `workerPoolRenderer`,
`bubblewrap`, `workerLaunchOptions`, and the types (`EditorPayload`, `EditorOrigins`, `PageData`,
`Manifest`…).

## `@puck-remote/core/react`

- `<PuckRemotePage page={page} />`: renders a `PreparedPage` (server component).
- `pageMetadata(page)`: `{ title, description, other }`, compatible with Next's `Metadata`.

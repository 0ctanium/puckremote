Every design choice in puck-remote follows from one premise: **theme authors are untrusted**
([D-0052](/docs/internal/decisions#D-0052)). A marketplace of third-party themes must be possible, so a theme
may be actively hostile.

## Actors

| Actor | Trusted? | Runs where |
|---|---|---|
| Theme code (`render`, adapter `toRequest`/`fromResponse`) | **No** | isolated-vm isolate, inside a permission-restricted worker process |
| Theme metadata (fields, defaults, queries, categories) | **No**, validated as data | Read from `manifest.json`, re-validated by the host with zod |
| Theme client scripts (`ctx.assets.script`) | **No** | The visitor's browser, on the **site** origin only |
| Host plugins (`DataSource`, `PageStore`, `ArtifactStore`, `CacheStore`, `AuthAdapter`) | Yes, chosen by the operator | Node, in the host process |
| The CLI on the developer's machine | Not by the host | The developer's machine; its output is re-checked |
| Editors | Authenticated and authorized per action | Their browser, on the **editor** origin |

## What a hostile theme cannot do

- **Run code on the host outside the isolate.** The host never builds or `import`s theme code. A
  static and runtime test enforces this (`no-dev-code.test.ts`).
- **Do I/O.** The isolate has no `fetch`, `process`, `require`, timers or host references. Data
  comes from [declarative queries](/docs/concepts/declarative-data) the host executes.
- **Reach arbitrary data.** Host queries only reach collections and fields the operator declared,
  with allowed operators and clamped limits ([host-source internals](/docs/internal/architecture/host-source)).
- **Steal secrets.** Secrets are substituted by the host after the isolate returns, and only for
  origins they are bound to. They never enter the isolate or the worker.
- **Do SSRF.** Outbound HTTP is https-only, allowlisted, origin-bound, DNS-pinned to public
  addresses, with manual same-origin redirects ([HTTP source](/docs/internal/architecture/http-source)).
- **Hang or crash the host.** CPU timeouts, a memory cap, a wall-clock watchdog, and a host-side
  SIGKILL of the worker process ([worker pool](/docs/internal/architecture/worker-pool)).
- **Run JavaScript in the editor.** The editor canvas is rendered on the server; the bundle is
  never served to browsers ([D-0080](/docs/internal/decisions#D-0080)).
- **Use an admin session from the public site.** Site and editor live on distinct origins,
  enforced per request ([surfaces](/docs/concepts/surfaces-and-origins)).
- **Forge slots.** Slot markers need a per-render nonce user content cannot know
  ([slots](/docs/concepts/slots)).

## Layers

Each layer assumes the previous one can fail.

| Layer | Stops | Status |
|---|---|---|
| V8 isolate, fresh context per request, CPU and memory limits | Theme JS reaching host APIs; runaway CPU/memory | always on |
| Worker processes (`--permission`, fs allowlist, empty env, heap cap, SIGKILL watchdog, recycling) | JS-level isolate escapes reaching secrets, files, network; crashes taking the host down | default |
| OS sandbox wrapper (`bubblewrap()`, Linux) | Native-code escapes | opt-in, experimental |
| Remote renderer | Native-code escapes, at infrastructure level | planned (M5) |
| Server-rendered editor | Theme JS in the editor origin | on |
| Separate site and editor origins | Theme scripts using admin sessions | required in production |
| CSRF (custom header + `Origin` allowlist) | Cross-site requests to the editor API | on |
| CSP and security headers | Script injection, framing, sniffing, unlisted third-party scripts | editor enforced, site report-only by default |

## Known limits

- isolated-vm is in maintenance mode, and a V8 escape runs native code, which Node's permission
  model does not constrain. Use the bubblewrap wrapper or (later) a remote renderer.
- Blocks within one request share a context and can influence each other.
- Theme client scripts don't run in the editor canvas (by design).

See [known gaps](/docs/internal/quality/known-gaps) for the full list.

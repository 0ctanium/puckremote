Every design choice in puck-remote follows from one premise: **theme authors are untrusted**
([D-0052](/docs/internal/decisions#D-0052)). A marketplace of third-party themes must be possible, so a theme
may be actively hostile.

## Actors

| Actor | Trusted? | Runs where |
|---|---|---|
| Theme code on the server (`render`, adapter `toRequest`/`fromResponse`) | **No** | isolated-vm isolate, inside a permission-restricted worker process |
| Theme code in the editor (`render` from `bundle.browser.js`) | **No** | The editor app's origin, another site: no cookies, no secrets |
| Theme metadata and pages | **No**, validated as data | Read from the artifact, hash-checked and re-validated by the host with zod |
| Theme client scripts (`ctx.assets.script`) | **No** | The visitor's browser, on the public site only |
| The editor app (Puck + bridge) | Holds no authority | The editor origin; can only send typed messages to the admin page |
| Host plugins (`DataSource`, `ArtifactStore`), the app's admin pages, RPC handlers and publish plugin | Yes, chosen by the operator | Node and the admin origin |
| The CLI on the developer's machine | Not by the host | The developer's machine; its output is re-checked |
| Editors | Authenticated by the app | Their browser: the admin page on the admin origin, the editor in the iframe |

## What a hostile theme cannot do

- **Run code on the host outside the isolate.** The host never builds or `import`s theme code. A
  static and runtime test enforces this (`no-dev-code.test.ts`).
- **Do I/O.** The isolate has no `fetch`, `process`, `require`, timers or host references. Data
  comes from [declarative queries](/docs/concepts/declarative-data) the host executes.
- **Reach arbitrary data.** Host queries only reach collections and fields the operator declared,
  with allowed operators and clamped limits ([host-source internals](/docs/internal/architecture/host-source)).
- **Steal secrets.** Secrets are substituted by the host after the isolate returns, and only for
  origins they are bound to. They never enter the isolate or the worker.
- **Do SSRF.** Outbound HTTP is https-only, allowlisted, origin-bound, DNS-pinned to public
  addresses, with manual same-origin redirects ([HTTP source](/docs/internal/architecture/http-source)).
- **Hang or crash the host.** CPU timeouts, a memory cap, a wall-clock watchdog, and a host-side
  SIGKILL of the worker process ([worker pool](/docs/internal/architecture/worker-pool)).
- **Use an admin session from the editor.** Theme components do run in the editor
  ([D-0192](/docs/internal/decisions#D-0192)), but on a separate, credential-free site that only admin
  origins may frame. They can only send protocol messages: `change` (data the admin decides to
  publish or not) and RPCs the admin page allow-listed, size- and rate-limited, run with the
  host's session ([editor protocol](/docs/internal/architecture/editor-protocol)). They cannot publish.
- **Use an admin session from the public site.** Public pages are refused on admin origins, and
  admin cookies are host-only ([origins](/docs/concepts/origins)).
- **Point the editor at other code.** The bridge only imports a bundle URL on an admin origin;
  the theme route serves only hash-verified files of a stored artifact.
- **Forge slots.** Slot markers need a per-render nonce user content cannot know
  ([slots](/docs/concepts/slots)).
- **Ship pages that bypass validation.** Pages are hash-checked like code and re-validated on
  read; `writePage` validates and strips resolved data before storing.

## Layers

Each layer assumes the previous one can fail.

| Layer | Stops | Status |
|---|---|---|
| V8 isolate, fresh context per request, CPU and memory limits | Theme JS reaching host APIs; runaway CPU/memory | always on |
| Worker processes (`--permission`, fs allowlist, empty env, heap cap, SIGKILL watchdog, recycling) | JS-level isolate escapes reaching secrets, files, network; crashes taking the host down | default |
| OS sandbox wrapper (`bubblewrap()`, Linux) | Native-code escapes | opt-in, experimental |
| Remote renderer | Native-code escapes, at infrastructure level | planned (M5) |
| Credential-free editor on its own site, `frame-ancestors` admin only | Theme JS in the editor using sessions | on when `origins` is configured |
| Typed protocol: origin **and** source checks, explicit target origins, allow-listed RPCs, size and rate limits | A framed or hostile editor driving the host | on |
| Admin origins distinct from the editor; public pages refused on admin origins | Theme scripts using admin sessions | on (config check, bindings) |
| Origin check on the RPC route | Cross-site requests to RPCs and publishing | on (`createEditorRpcRoute`) |
| CSP and security headers | Script injection, framing, sniffing, unlisted third-party scripts | admin enforced, site report-only by default |
| Draft data only through the editor's RPC; public renders use `public` mode | Unpublished content leaking to visitors | on |

## Known limits

- isolated-vm is in maintenance mode, and a V8 escape runs native code, which Node's permission
  model does not constrain. Use the bubblewrap wrapper or (later) a remote renderer.
- Blocks within one request share a context and can influence each other.
- Theme client scripts don't run in the editor canvas (by design).
- Theme code in the editor sees the page being edited and the draft data RPCs return for it, and
  can send `change` messages with arbitrary (validated) page data. What gets published is still
  the admin's action, through the host UI.
- Authorization is entirely the app's: a handler of `createEditorRpcRoute` or a publish action that
  forgets its session check is open to anyone on the admin origin.
- The editor origin's isolation depends on it being another **site**; a subdomain of the app's
  registrable domain could receive `Domain=` cookies.

See [known gaps](/docs/internal/quality/known-gaps) for the full list.
